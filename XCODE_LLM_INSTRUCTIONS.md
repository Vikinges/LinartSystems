# Задача для LLM-разработчика (Xcode): iOS-приложение Linart Systems Reports

Этот файл — полная инструкция для LLM, работающего в Xcode. Следуй ей строго.
Цель: нативное iPhone-приложение для сотрудников: создание сервисных отчётов,
работа офлайн, синхронизация с сервером компании, отправка отчётов клиенту на подпись.

---

## 1. Технологический стек (обязательно)

- Swift 6, SwiftUI, **iOS 26 минимальный таргет** (на июнь 2026 iOS 26 стоит на ~79%
  всех iPhone и 86% устройств последних 4 лет; парк служебных телефонов — iPhone 12+).
  Это открывает SpeechAnalyzer, Translation, Foundation Models, RecognizeDocumentsRequest,
  PaperKit и BGContinuedProcessingTask без legacy-веток.
- Только `async/await` — никаких completion handlers и Combine для новой логики.
- Персистентность: SwiftData (или Core Data, если нужна тонкая настройка миграций).
- Сеть: `URLSession` (background configuration для загрузок), без сторонних HTTP-библиотек.
- Многомодульный проект через Swift Package Manager (см. раздел 5).
- Никаких сторонних зависимостей без явного разрешения владельца проекта.

## 2. Серверная архитектура (что уже существует)

```
Интернет → traefik (TLS, Let's Encrypt, домен lsc-led.de)
              └── hub :8080        — авторизация, UI, reverse-proxy
                    ├── service2 :3001      — отчёты, PDF, файлы (только внутр. сеть)
                    ├── service-sign :3002  — подпись клиентом по ссылке
                    └── paddle-ocr :8866    — OCR (внутр.)
```

- Hub проксирует `/service2/*` → `service2` (префикс переписывается: `/service2/submit` → `/submit`).
- service2 и service-sign связаны общим volume `sign-data` и внутренним
  эндпоинтом `POST /internal/jobs` (заголовок `X-Internal-Token`).
- Версия service2: `SERVICE2_VERSION` в `service2/server.js` (сейчас 0.39).

### 2.1 Авторизация

| Уровень | Механизм | TTL |
|---|---|---|
| Hub (пользователи) | `POST /admin/login`, подписанные HMAC-SHA256 cookie (`httpOnly`, `sameSite=lax`) | 7 дней |
| service2 (админ-API) | Bearer-токен: `Authorization: Bearer <token>` или `X-Admin-Token` | 24 часа |

- Роли пользователей hub: `admin`, `manager`, `blocked`; плюс `allowedServices` и флаг доступа к файлам.
- Hub передаёт downstream-заголовки: `X-Hub-Role`, `X-Hub-Can-Delete-Files`, `X-Hub-Can-Generate-Links`.
- Rate limit логина: 10 попыток / 10 минут → ожидай HTTP 429.
- **Мобильный клиент использует Bearer-токены** (реализовано на сервере):
  `POST /api/auth/token` `{username, password}` → `{ok, token, tokenType, expiresAt, user}`.
  Токен (TTL 7 дней) слать в `Authorization: Bearer <token>` — работает на ВСЕХ
  маршрутах hub, включая прокси `/service2/*`. Обновление: `POST /api/auth/refresh`
  (с действующим токеном; права перечитываются из хранилища пользователей).
  Проверка сессии: `GET /api/auth/me`. Токен хранить только в Keychain.

### 2.2 Ключевые эндпоинты (через hub, base = `https://lsc-led.de`)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/status` | Статус всех сервисов |
| POST | `/api/auth/token` | **Логин для мобильного клиента** → Bearer-токен |
| POST | `/api/auth/refresh` | Обновить токен (требует действующий токен) |
| GET | `/api/auth/me` | Текущий пользователь и права |
| POST | `/admin/login` | Логин через cookie (web; мобильному не нужен) |
| POST | `/api/logout` | Выход (cookie-сессия) |
| GET | `/service2/health` | Health service2 |
| POST | `/service2/submit` | Отправка отчёта (multipart/form-data, поддерживает `client_report_id`) |
| GET | `/service2/suggest?field=&q=` | Подсказки автозаполнения |
| GET | `/service2/projects/:projectKey` | Карточка проекта (автозаполнение site info) |
| GET | `/service2/api/files?type=&limit=&offset=&...` | Список PDF: фильтры + пагинация, ответ содержит `total`, `offset`, `limit` |
| GET | `/service2/download/:type/:file` | Скачать PDF |
| POST | `/service2/api/files/delete` | Удалить файлы (только admin) |
| POST | `/service2/api/files/zip` | ZIP выбранных файлов (только admin) |
| POST | `/service2/api/sign/create` | Создать задание на подпись, вернуть ссылку |
| GET | `/service2/api/sign/jobs?status=&limit=&offset=` | Список заданий на подпись со статусами |

Подпись клиентом (публично, base = `https://lsc-led.de/sign`, hub проксирует `/sign` → service-sign):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/sign/s/:token` | Страница подписи |
| POST | `/sign/s/:token/verify-pin` | Проверка 6-значного PIN (urlencoded) |
| GET | `/sign/s/:token/pdf` | Просмотр PDF (требует PIN) |
| POST | `/sign/s/:token/submit` | Отправка подписи (требует PIN) |
| GET | `/sign/s/:token/download` | Скачать подписанный PDF |

Токены: 32 случайных байта base64url, SHA-256-хэш в SQLite, PIN из 6 цифр, TTL 1–7 дней,
rate limit на все маршруты. Статусы задания: `pending` → `signed` | `expired`.

### 2.3 Формат отчёта `/submit`

- `multipart/form-data`, всего 122 поля — канонический список: `service2/fields.json`
  (НЕ хардкодить в приложении список целиком — генерируй модель из fields.json).
- Группы полей: данные клиента (`end_customer_name`, `site_location`,
  `date_of_service`, `lsc_project_number`, `batch_number`…), 7 пунктов LED-инспекции,
  5 контрольных пунктов, 2 spares, 15 строк parts (по 5 полей), sign-off инженера
  и клиента, daily report (`project number`, `date`, `submitter`, текст).
- Сотрудники: массив `employees[n][...]`; уникальность считается по `group`,
  fallback `name + role`.
- Фото-поля: `photo_before`, `photo_after`, `photos`, `daily_photos`,
  `photo_defects`, `photo_installation` (до 20 каждое). Лимиты: 128 MB/файл,
  512 MB суммарно, максимум 64 файла, только JPEG/PNG.
- Клиент ОБЯЗАН сжимать фото перед отправкой: JPEG, длинная сторона ≤ 1600 px
  (так делает web-клиент — поведение должно совпадать).
- Успешный ответ: `{ "ok": true, "url": "/download/...pdf", ... }`; ошибка: `{ "ok": false, "error": "..." }`.

## 3. Функциональные требования приложения

1. Логин (роль определяет UI: manager — отчёты и свои файлы; admin — всё).
2. Создание отчётов двух типов: Service Report (полная форма) и Daily Report.
3. Автозаполнение: карточка проекта по номеру (`/projects/:key`), подсказки (`/suggest`).
   Кэшировать локально для офлайна.
4. Фото: камера + галерея, сжатие на устройстве, привязка к черновику отчёта.
5. Архив файлов: список PDF с фильтрами, просмотр (PDFKit), скачивание.
6. Только admin: удаление файлов, ZIP, подгрузка/редактирование файлов с сервера,
   управление заданиями на подпись.
7. Отправка на подпись: после генерации PDF — кнопка «Send for signature»,
   создание ссылки (`/api/sign/create`), шеринг через share sheet, статусы
   заданий с сервера (`/api/sign/jobs`: `pending/signed/expired`).

## 3.1 Голосовой ввод, OCR и on-device AI (ОБЯЗАТЕЛЬНО — всё офлайн, без сторонних облаков)

Пользователи — монтажники на шумных объектах (немецкий, английский, русский, польский).
Актуально на июнь 2026, всё работает on-device:

### Диктовка (Speech framework, iOS 26)
- Длинные тексты (текст daily report, комментарии): `SpeechAnalyzer` + `SpeechTranscriber` —
  полностью офлайн, без лимита длительности, авто-пунктуация, стриминг через `AsyncSequence`
  (volatile-результаты показывать серым, финальные — чёрным; текст никогда не «мигает»).
  Языки on-device: de_DE/de_AT/de_CH, en_*, ru_RU. **Польского НЕТ.**
- Короткие поля и техтермины: `DictationTranscriber` + `contextualStrings`
  (номера партий LED, названия объектов) — `SpeechTranscriber` контекстные словари НЕ поддерживает.
- Польский: fallback на `DictationTranscriber` (проверять `supportedLocales`) или модуль
  WhisperKit (MIT, поддерживает авто-определение языка) — подключать только при реальной нужде.
- Автоопределения языка в SpeechAnalyzer НЕТ: хранить язык в профиле пользователя +
  переключатель языка рядом с кнопкой микрофона. Один язык на сессию диктовки.
- Системный микрофон клавиатуры оставить включённым на всех полях (бесплатный
  смешанный ввод клавиатура+голос).
- Все транскрипты прогонять через доменный словарь: regex-нормализация номеров
  партий/серийников, фаззи-коррекция терминов.
- Модели языков скачивать заранее через `AssetInventory` (на Wi-Fi). Требуется iPhone 12+.
- Обрабатывать прерывания `AVAudioSession` (Bluetooth-гарнитуры, звонки).

### Перевод (Translation framework)
- On-device перевод de/en/ru (+pl) в любых парах после скачивания моделей —
  работает в самолётном режиме. `TranslationSession(installedSource:target:)` (iOS 26)
  вызывается из чистой логики без SwiftUI-модификаторов.
- Сценарий: работник пишет/диктует по-русски → поле отчёта переводится на en/de.
- Скачать 3-4 языковые модели при первом запуске (Wi-Fi); всегда проверять
  `LanguageAvailability.status(from:to:)` и предлагать докачку.

### OCR с камеры (Vision/VisionKit)
- Серийники/этикетки в поля формы: `DataScannerViewController` (live-сканер,
  tap-to-capture) для латиницы и штрих/QR-кодов; для кириллицы — `RecognizeTextRequest`
  по кадру (поддерживает ru/de/en). Результат фильтровать regex'ом формата серийника.
- Бумажные формы/таблицы на коробках: `RecognizeDocumentsRequest` (iOS 26) — читает
  структуру документа (таблицы, списки) за один проход.
- Где есть штрихкод/QR — предпочитать его OCR'у.

### On-device LLM (Foundation Models, iOS 26)
- `LanguageModelSession` + `@Generable`/`@Guide` (guided generation): «причесать» надиктованный
  черновик в формальный текст отчёта, суммаризация, разбор свободного текста в структурные поля.
- Ограничения: en/de сейчас, русский придёт с iOS 27 (осень 2026); контекст 4096 токенов;
  только iPhone 15 Pro+ с включённым Apple Intelligence — ВСЕГДА проверять
  `SystemLanguageModel.default.availability` и тихо скрывать фичу, если недоступно.
- Это удобство, не зависимость: приложение полностью функционально без LLM.

### Подпись клиента на месте (офлайн-вариант)
- Кроме ссылки на подпись (онлайн-поток через service-sign) — локальная подпись
  на экране: `PKCanvasView` (PencilKit) → изображение → `PDFAnnotation` в PDF (PDFKit).
  Опционально iOS 26 `PaperKit` для системных инструментов разметки.

## 4. Офлайн-режим и синхронизация (ОБЯЗАТЕЛЬНО)

Приложение обязано полноценно работать без интернета и синхронизироваться при его появлении.

- Offline-first: КАЖДЫЙ отчёт сначала сохраняется локально (SwiftData), затем синхронизируется.
- Статусы локального отчёта: `draft` → `queued` → `uploading` → `synced` | `failed`.
- Outbox-паттерн: отдельная очередь `SyncQueue` (actor) хранит задания на отправку;
  обработка строго по одному, FIFO, с экспоненциальным backoff при ошибках.
- Идемпотентность (реализовано на сервере): каждый отчёт получает UUID на устройстве
  и отправляется в `/submit` полем `client_report_id`. Повтор с тем же id не создаёт
  дубликат — сервер вернёт сохранённый результат с флагом `duplicate: true`.
  Повтор во время обработки первого запроса → HTTP 409 `duplicate_in_progress` (повторить позже).
- Мониторинг сети: `NWPathMonitor`; при появлении сети — автоматический запуск очереди.
- Фоновая отправка: `URLSession` background configuration + `BGContinuedProcessingTask`
  (iOS 26) — загрузка отчёта с фото продолжается после сворачивания приложения
  с системным прогресс-индикатором; `BGProcessingTask` для плановой досинхронизации.
- Фото хранятся в `Application Support/reports/<uuid>/`, в БД — только пути.
- Кэш для офлайна: projects.json, подсказки suggest, список своих файлов.
- Конфликты: отчёты append-only, конфликтов записи нет; справочники — server wins.
- UI всегда показывает состояние синхронизации (бейдж на отчёте + общий индикатор).
- Ничего не удалять локально, пока сервер не подтвердил приём (`ok: true`).

## 5. Архитектура и независимость модулей (ОБЯЗАТЕЛЬНО)

Многомодульный SPM-проект. Правило зависимостей: Feature-модули зависят ТОЛЬКО от
Core-модулей и только через протоколы. Feature → Feature импорты ЗАПРЕЩЕНЫ.

```
App                  — композиция, DI-контейнер, навигация
├── CoreModels       — чистые модели (Codable, Sendable), без зависимостей вообще
├── CoreNetworking   — APIClient (протокол + реализация), endpoints, без UI
├── CorePersistence  — SwiftData-схема, репозитории (протоколы + реализации)
├── SyncEngine       — очередь синхронизации (actor), зависит от Networking+Persistence
├── DesignSystem     — цвета, шрифты, переиспользуемые View
├── FeatureAuth      — экран логина, сессия
├── FeatureReports   — формы отчётов, черновики
├── FeatureFiles     — архив PDF, просмотр
└── FeatureSign      — отправка на подпись, статусы
```

- DI только через инициализаторы (`init(api: APIClientProtocol, ...)`).
- Синглтоны запрещены. Исключение: логгер и часы — и те за протоколами.
- Каждый Feature-модуль обязан компилироваться и тестироваться изолированно.
- Связь между фичами — только через навигацию в App-слое.

## 6. Стандарты кода (ОБЯЗАТЕЛЬНО)

### Читаемость
- Имена полные и говорящие: `submitServiceReport()`, не `subSR()`. Без сокращений.
- Функция ≤ 40 строк, делает РОВНО одну вещь. Файл ≤ 300 строк, один тип на файл.
- Вложенность ≤ 2 уровней — используй guard и ранний выход.
- Запрещены: `!` (force unwrap), `try!`, `as!`, пустые `catch`, magic numbers.
- Каждый публичный тип и метод — doc-комментарий `///` (зачем, не что).
- SwiftLint + SwiftFormat в проекте, сборка с warnings-as-errors.

### Атомарное программирование
- Бизнес-логика — чистые функции: вход → выход, без побочных эффектов.
  Side effects (сеть, диск, время) изолированы за протоколами на границах.
- Каждая единица работы атомарна: один коммит = одна завершённая, компилируемая,
  протестированная единица. Не смешивать рефакторинг и новую функциональность.
- Любая операция с данными либо завершается целиком, либо откатывается
  (черновик не может оказаться наполовину сохранённым).
- Состояние — иммутабельные структуры; мутации только в одном месте (ViewModel/actor).

### Паттерны
- MVVM: View (тупой, декларативный) → ViewModel (`@Observable`, вся логика) → Services.
- Concurrency: `actor` для SyncEngine и общего состояния; типы через границы — `Sendable`.
- Ошибки: типизированные enum-ошибки на модуль (`NetworkError`, `SyncError`),
  каждая ошибка либо обработана, либо показана пользователю — никогда не проглочена.

### Тесты
- Unit-тесты на каждый модуль: парсинг ответов API, очередь синхронизации
  (повторы, backoff, идемпотентность), валидация формы, подсчёт сотрудников.
- В unit-тестах сети нет — только стабы `APIClientProtocol`.
- Минимум: каждая публичная функция Core/Sync покрыта тестом.

### Definition of Done (для каждой задачи)
1. Компилируется без warnings. 2. Тесты зелёные. 3. SwiftLint чистый.
4. Работает офлайн, если применимо. 5. Dark mode + Dynamic Type не сломаны.
6. Локализация: en (база), de, ru.
